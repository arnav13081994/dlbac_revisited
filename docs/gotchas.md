# Gotchas

Things that cost time and are not obvious from the code.

1. **Which columns the network sees.** For datasets with more than 8 metadata fields per side the DLBAC paper's text says the first 8 user and first 8 resource fields are exposed. The released script (`external/DlbacAlpha/neural_network_training/dlbac_alpha_resnet.py`) deletes `slice(8, 8 + hide)` with `hide = columns - 20`, which removes the user fields beyond 8 and the first resource fields. It exposes user fields 0-7 and the last 8 resource fields (19k: resource 2-9; 21k and 20k: 3-10; 22k and 28k: 5-12). We follow the code (`dlbac.load`), which is what produces numbers close to the published figures. The equality indicators use all 64 pairs of the visible fields, so they do not depend on this choice, but the baselines and the ResNet do.
2. **Keras `padding='same'` is not torch `padding=k//2` for stride 2.** TensorFlow pads `max((ceil(n/s) - 1) * s + k - n, 0)` in total per axis with the odd pixel after (right/bottom). A 3x3 stride-2 convolution on an even size pads (0, 1); torch pads (1, 1) and samples a lattice shifted by one pixel. With the authors' shipped weights `dlbac.Conv2dTF` (option `tf_same=True`) gives F1 0.98 and symmetric padding 0.39 (`make e2`). All ResNets in `results/` use `tf_same=True`. Odd sizes, stride 1 and 1x1 convolutions are unaffected.
3. **h5py is needed only for `make e2`** (it reads the authors' Keras weights); it is in `requirements-port.txt`, not in `requirements.txt`.
4. **Pin library threads to 1 before importing numpy.** scikit-learn's OpenMP (`HistGradientBoostingClassifier`) and BLAS ignore a `--threads` option and take every core unless `OMP_NUM_THREADS` and friends are set before the library loads. Several concurrent jobs each spinning all cores made one gradient-boosting fit about 20 times slower. `run_cell.py` sets the variables before `import numpy`; keep that order if you add a script that runs in a pool. Check `uptime` a few minutes after starting a pool: the load should be close to the number of running processes.
5. **A job queue must repeat its "already done / already running" check after it waits for a free slot.** The first version checked only before waiting, so a queue that blocked for hours then started a cell another queue had finished meanwhile. Two stored cells were run twice for this reason (E1 u5k-r5k-auth12k seed 4 `resnet_eq`: the later run overwrote the earlier one; F1 u4k-r7k-auth20k seed 3 `svm`: the duplicate was stopped). `jobqueue.py` now repeats the check, and `tests/test_jobqueue.py` fails on the pre-fix version kept in `tests/fixtures/`.
6. **Run Python with `-I`.** The scripts add their own folder to `sys.path`, so isolated mode (which ignores `PYTHONPATH`, the current directory and user site-packages) is safe and keeps results independent of what else is installed. `jobqueue.py` recognises running jobs by the text ` -I src/` and a trailing `--out <file>.json` in their command line, so keep both in any job line you write by hand.
7. **`VIRTUAL_ENV` leaks into subprocesses.** Job lines start with `env -u VIRTUAL_ENV ./.venv/bin/python` so that a job never installs into or imports from another environment.
